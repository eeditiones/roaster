Validating requests with Fore

A Roaster operation can point to a Fore page. The server reads the binds of that page and checks the request body against them, so the rules are written once and enforced on both sides.

This page is that Fore page. The browser runs the form below. The server compiles the same fx-bind elements into an XQuery validator for POST api/fore/demo. Everything else on the page, like this text, is ignored by the server.

The binds

These are the fx-bind elements of this page, listed from the page itself. Fore uses them in the browser, and the server compiles the same ones. They are the only place the rules and their messages are written. 

This list needs JavaScript.

Enable it for an operation

Add the vendor extension x-fore to the operation in your api.json. The path is relative to the app. 

"/api/fore/demo": {
    "post": {
        "operationId": "api:create-order",
        "x-fore": "resources/fore-validation.html",
        ...
    }
}

Then pass the middleware to the router. Keep the standard authorization first.

import module namespace fore = "http://e-editiones.org/roaster/fore-validation";

roaster:route($definitions, $lookup, (auth:standard-authorization#2, fore:validate#2))

If the body is valid the handler runs as usual. If not, it is never called and the response is a 422: 

{
    "description": "Validation failed",
    "value": {
        "errors": [
            { "ref": "amount[1]", "bind": "amount", "kind": "constraint",
              "alert": "The amount must be a whole number from 1 to the limit" }
        ]
    }
}

What is checked

The default instance, the fx-instance without an id, describes the request body. For every node selected by an fx-bind:

AttributeMeaning on the server
requiredAn XPath expression. If it is true the node must not be empty.
constraintAn XPath expression that must be true.
typeThe value must be castable to the XML Schema type. Empty values are left to required.
relevantFor a node that is not relevant, required, constraint and type are skipped. Fore 5.2 still counts an empty required node that is not relevant as invalid, so prefer an expression in required, like the note above.
alertThe message returned for a violation, also as child element fx-alert.

Binds nest like in Fore. If a type is wrong only the type is reported, not also the constraint. An expression that raises an error, for example because a tampered value can not be compared, counts as a violation, it never fails the request.

HTML input types

Fore reads the native validity of the widget, so an <input type="email"> is checked by the browser. The server applies the same rule, taking the type from the control that edits the node, so Email and Delivery above need no rule in their binds. The message is the alert of the bind, or "Please enter a valid email" if it has none.

Input typeValid value
emailAn address like the HTML specification allows: ann@example.org
urlAn absolute URL: https://example.org/path
date2030-12-31, and a date that exists
time09:30 or 09:30:15.5
datetime-local2030-12-31T09:30
month, week2030-12, 2030-W07
number, rangeA floating-point number like -12.5e3
color#a0b1c2

Other types, like text or tel, have nothing to check. Empty values are left to required. A control belongs to a bind if its ref is the ref of the bind or the path of nested bind refs. The attributes min, max, step and pattern are not checked on the server, use a constraint for those, or a type such as xs:date to check a value without a control.

Other instances

Rules can read other instances with instance('id') or $id, like $rates and instance('limits') above. The request is the only input: all other instances are taken from this page, from a src relative to it or inline, never from the request. In a browser an inline XML instance is parsed as HTML, which is why this page loads its instances with src. A tampered client can therefore not change the data its own rules are checked against. Binds that start on another instance are not validated.

Functions and comparisons

Fore runs expressions with fontoxpath, the server with eXist. To make sure a form is never validated with different rules, a page may only call functions from the fn, math, map, array and xs libraries. Anything else, like now(), makes compiling the page fail with a message that names the bind and the function.

Nodes have no type on the server, so comparing two nodes compares their text and "5" <= "10" is false, as in Fore. Cast explicitly: number(.) <= number(instance('limits')/max).

How it works

  • On the first request the binds are compiled to XQuery and stored in the collection fore-cache of the app.
  • The compiled validator is used until this page changes. Editing the page takes effect on the next request.
  • If the cache can not be written, the page is compiled on each request and a warning is logged.
  • The page has to be well-formed XML, because eXist reads it as a document.
